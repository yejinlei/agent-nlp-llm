01

🕳️ 指令被埋在长上下文的最底下

结构坑 lost in the middle 高频
❌ 错误示例 
[一篇 6000 字的用户访谈记录全文……]
[又一段 3000 字的产品背景介绍……]
[再一段 2000 字的竞品分析……]

请从上面的访谈记录中提取所有用户提到的痛点，按主题分组，并给出优先级排序，输出 JSON。
🔬 原理：注意力对上下文中段的天然衰减

Transformer 的注意力权重分布呈现出典型的 U 形曲线——序列开头和结尾的 token 获得最多关注， 中间部分被稀释，这就是著名的 lost in the middle 现象。

  • 开头 sink 效应：第一个 token（BOS）往往吸收了大量注意力作为"注意力汇"，系统性地获得高权重。
  • 结尾 recency 效应：语言模型的预训练目标是从上文预测紧随其后的 token，因此靠近生成位置的内容天然更相关、权重更高。
  • 位置编码的相位：RoPE 下不同位置的相对距离会影响点积，长距离内容的相关性信号进一步被削弱。
\(\text{Attn}(Q,K,V) = \text{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V\) —— 中段位置在 QK^{\top} 上既没有 sink 的偏置优势，也没有 recency 的语义优势，softmax 归一化后权重被摊薄。

结果：指令虽然写在了 prompt 里，但在注意力层面被前面 11000 字的材料淹没了。 模型"看到"了指令，但没"在意"它。

✅ 正确做法：指令前置 + 结构分隔 + 结尾复述 
# 任务
从下面的访谈记录中提取用户痛点，按主题分组并排序优先级。
只依据下面 <访谈记录> 中的内容作答，不要引入外部信息。

# 输出格式（严格）
{"themes":[{"name":"...","pain_points":["..."],"priority":1}]}

# 约束
- priority 取 1-5，1 为最高
- 每条痛点必须是访谈记录中的原话或紧邻转述
- 若记录中未提及某主题，不要编造

# 输入材料
<访谈记录>
[6000 字段落……]
</访谈记录>

# 现在开始执行上面的「任务」，输出 JSON：
❌ 指令在最后 模型容易只回答"最近看到的材料片段的摘要"，漏掉中段信息；复杂约束（分组 / 排序 / 格式）常被整体忽略。
✅ 指令首尾呼应 开头定义任务与格式（利用 sink 位），结尾再复述一次动作（利用 recency 位），中段只放数据。实测约束遵循率能从 ~60% 提升到 ~90%+。
🩺 经验法则：「首尾放指令，中间放数据」。 更激进一点的做法是把长文档做成 RAG，只把最相关的 Top-K 片段喂进去——减少"中段"的物理长度，从根本上绕开这个坑。
02

🚫 "不要写…"反而让模型写得更起劲

原理坑 否定式指令 / 语义激活 高频
❌ 错误示例 
写一段介绍我们咖啡机产品的话。
不要用"高品质""匠心""极致体验"这种空洞的词。
不要写得太长。
不要用感叹号。
不要提到价格。
🔬 原理：否定词的"概念注入"效应

语言模型是基于共现统计训练的，它学到的是"哪些词倾向于出现在哪些上下文里"。 当你说"不要用『高品质』"，这些 token 本身仍然被实体化地写进了上下文：

P(x_t \mid \text{"不要用高品质匠心极致体验……"}) —— 上下文里已经出现了"高品质""匠心""极致体验"，模型的下一 token 分布被这些词语义激活， 反而抬高了它们的生成概率。

这类似心理学里的"白熊效应"：告诉你"别想白熊"，你脑子里立刻全是白熊。模型没有"抑制"这个操作， 它只有"基于上下文预测下一个 token"。否定词 不要 是一个很弱的修饰， 远弱于被否定的内容本身的语义强度。

  • 更糟的情况：当 prompt 里"不要 X"出现多次，模型会误判话题域——它会觉得"这个对话是关于高品质咖啡机的"，于是往那个方向写。
  • 约束越具体、越负面，注入越强。四个"不要"，等于给模型喂了四组它本该避开的词。
✅ 正确做法：换成正面、可执行的规格 
写一段介绍我们咖啡机产品的话。

风格要求（正面描述）：
- 用具体的物理参数说话：15 bar 泵压、92°C 恒温、2L 水箱、预热 25 秒
- 用具体使用场景说话：早上赶时间、办公室小桌、给父母用
- 句式为短陈述句，每句不超过 25 字
- 长度控制在 120-160 字
- 语气平实、信息密度高，像产品规格说明
❌ 负面清单 输出："我们的咖啡机拥有高品质的…带来极致体验！"——四条禁令全中，还附赠感叹号。
✅ 正面规格 输出："15 bar 泵压让浓缩油脂更厚。92°C 恒温萃取，2L 水箱够一家人用一周。预热只要 25 秒，早上不用等。"——参数与场景齐备。
💡 唯一该用否定式的场景：安全边界（"不得提供医疗诊断""不输出个人隐私信息"）。 这类约束通常配合系统提示词并且会被专门对齐训练，效果比普通否定指令好得多。 其余场景，一律翻译成"要做什么"。

📐 要 JSON 但没说清形状，解析全线崩溃

格式坑 结构化输出 高频
❌ 错误示例 
把下面这段评论分析一下，输出 JSON。

评论：这款耳机音质很好，但是戴久了耳朵疼，而且价格偏贵，不太推荐。

输出：

实际输出（真实会发生）：

好的，这是分析结果：

```json
{
  "情感": "混合",
  "优点": ["音质好"],
  "缺点": ["佩戴不适", "价格高"],
  "建议": "不建议购买"
}
```

希望对你有帮助！需要我进一步分析其他评论吗？
🔬 原理：模型在"对话分布"里采样，不在"序列化器"里采样

模型被训练成乐于助人的对话助手。它的训练数据里，"输出 JSON"这类请求的旁边常常跟着寒暄、解释、代码围栏。 你没指定形状时，它就按"最像人类回应的方式"生成——于是有了开场白、```json 围栏、结束语。

  • 字段名不确定：你说"输出 JSON"，模型可能用 sentiment、也可能是 情感、emotion、polarity。下游 json.loads() 立刻 KeyError。
  • 类型不确定："缺点"是数组还是逗号分隔字符串？"评分"是 1-5 整数还是 "极高"？
  • 包装层不确定：```json 围栏、前后寒暄，都会让严格 JSON 解析器直接抛异常。
  • 空值不确定：字段缺失时是省略、是 null、还是 ""？
✅ 正确做法：给 schema + 给样例 + 禁止包装 + 用原生结构化输出 
分析下面的评论，只输出一个 JSON 对象。不要输出任何解释、寒暄或 Markdown 代码围栏。

Schema（字段名、类型、取值范围必须严格遵守）：
{
  "sentiment": "positive" | "negative" | "mixed",
  "pros": string[],      // 每条不超过 15 字，没有则空数组
  "cons": string[],      // 同上
  "score": number,       // 1-5 的整数
  "recommend": boolean,
  "reason": string       // 一句话，不超过 40 字
}

Few-shot 样例：
输入：做工精细，续航一般。
输出：{"sentiment":"mixed","pros":["做工精细"],"cons":["续航一般"],"score":3,"recommend":false,"reason":"优点与短板并存，适合轻度使用。"}

现在处理这条：
输入：这款耳机音质很好，但是戴久了耳朵疼，而且价格偏贵，不太推荐。
输出：
❌ 只说"输出 JSON" 期望与实际不一致，字段名/类型/包装层全靠猜。生产环境解析失败率常达 10%–30%。
✅ Schema + few-shot 字段名与类型被钉死，样例给模型一个可模仿的模板，配合 response_format / JSON Schema Mode（OpenAI、vLLM 等均支持）可以做到 100% 可解析。
⚠️ 工程侧双保险：① 优先使用 API 提供的结构化输出能力（约束解码，token 级保证合法）； ② 无此能力时，写一个"解析 + 正则修复 + 重试"的兜底函数：剥离 ``` 围栏、截取第一个 { 到最后一个 }、 失败则带上错误信息再请求一次。别让 JSON 解析失败直接打崩线上服务。

☠️ Few-shot 示例有毒，越教越歪

原理坑 上下文学习 / 分布对齐
❌ 错误示例 
判断下面句子的情感（positive / negative）：

句子：服务态度很差，等了一个小时。 → positive
句子：物流很快，包装完好。 → positive
句子：东西不错。 → positive

句子：这家店我再也不来了。 →
🔬 原理：few-shot 示例定义的是"任务分布"，不是"任务说明"

上下文学习（In-Context Learning）的机制不是"理解规则"，而是从示例中归纳出输入→输出的映射模式。 模型会寻找示例里最一致的规律——如果三个示例的答案都是 positive，最省力的规律就是 "答案永远是 positive"。

  • 标签不平衡：3 个 positive 打头，模型会先验偏向 positive。要让示例覆盖所有类别且分布均衡。
  • 示例本身有错：第一个示例是明确负面却标成 positive，相当于教模型"情感标签可以乱贴"。
  • 表面特征被当成规律：如果所有 positive 示例都以句号结尾、所有 negative 都以感叹号结尾，模型可能学的是标点，而不是情感。
  • 顺序敏感：研究表明 few-shot 示例的排列顺序会导致准确率波动 10%–20%（recency bias 让最后一个示例影响最大）。
P(y \mid x, \text{demos}) \;\approx\; P(y \mid \text{归纳出的模式}) —— 示例是证据，模型从这里估计的是条件分布，不是逻辑规则。
✅ 正确做法：均衡、正确、多样、格式一致 
判断句子的情感，输出 positive 或 negative。只输出这一个词。

---
句子：菜品很新鲜，上菜也快。 → positive
---
句子：等了四十分钟还没人理我。 → negative
---
句子：环境一般，味道还行。 → positive
---
句子：结账时多算了一道菜。 → negative
---

句子：这家店我再也不来了。 →
❌ 3 个同标签 + 1 个错标 模型学到"一直输出 positive"，或学到"情感标签随机"。准确率可能还不如零样本。
✅ 2 正 2 负 + 交错排列 类别均衡、正误明确、句式多样，模型能稳定归纳出边界。示例顺序打乱做多次评测取平均，避免顺序偏差。
🩺 自查清单：① 每类样本数量是否均衡？② 示例标签 100% 正确吗（人工再过一遍）？③ 换一下示例顺序，结果还稳定吗？ ④ 去掉示例后（zero-shot）表现如何？如果 zero-shot 更好，说明你的示例在捣乱。

📦 关键约束被淹没在一堆口水话里

结构坑 约束与噪声的比例 高频
❌ 错误示例 
你好！我是一个产品经理，最近在做一个 B 端 SaaS 项目，我们想做一个帮助用户快速了解我们产品的介绍文案。
我们的产品是给中小企业的财务对账工具，主要解决月底对账要花三天的痛点。
目标用户是财务专员和会计，他们一般不太懂技术，所以文案要通俗一点。
哦对了，最好别超过 100 个字，因为我们 UI 上位置不大，而且我们是多语言产品所以中文版最多 100 字。
希望语气是专业但不冰冷，像个懂行的同事在跟你说话。
谢谢！
🔬 原理：约束的"信噪比"太低

模型的注意力预算有限。prompt 里真正重要的约束只有两三条（≤100 字、通俗、专业但亲切）， 但它们散布在 200 多字的背景介绍、礼貌用语和口语化叙述里，权重被平均掉了。

  • 关键数字被埋：100 字 出现在一句话的中间，前面还有"哦对了""最好别超过"。模型可能只记住"别太长"。
  • 口语化标记弱："希望""最好""一般"都是软性语气词，模型不容易把它们识别为硬约束。
  • 信息重复但不一致："目标用户不太懂技术"和"语气专业但不冰冷"是两条不同约束，混在一段里会互相干扰。
  • 礼貌寒暄消耗 token：这些 token 也会参与注意力计算，造成纯噪声。
✅ 正确做法：结构化 + 关键约束显式编号 + 硬性边界用大写强调 
## 任务
为 B 端财务对账 SaaS 产品写一段产品介绍文案。

## 目标读者
中小企业财务专员 / 会计（非技术背景）

## 硬性约束（必须全部满足）
1. **总字数 ≤ 100 字**（中文汉字计数，标点不计）
2. 提及核心痛点：月底对账耗时约 3 天
3. 不得出现技术术语（如 API、SDK、集成）
4. 全文不使用感叹号

## 语气
专业但不冰冷，像一位懂行的同事在介绍。

## 输出
只输出文案正文，不要标题、不要解释、不要引号。
❌ 一段口水话 输出常见 180–250 字，带标题和"我们致力于…"套话，字数约束基本失守。
✅ 结构化约束 输出 88 字左右，痛点明确，无术语无感叹号。约束遵循率大幅提升。
💡 三条结构原则：① 用 Markdown 标题分块，让模型能"看到"结构； ② 硬约束编号并列，数字约束加粗；③ 把"必须/不得"和"希望/尽量"区分开—— 硬约束不超过 5 条，多了模型必然漏掉几条。

🧮 让模型心算多步数学题，不给草稿纸

原理坑 思维链 / 串行计算能力
❌ 错误示例 
小明有 48 个苹果，他给了小红 1/3，然后小红把自己的苹果平均分给 4 个朋友，
每个朋友又给了小明 2 个。请问最后小明有多少个苹果？只回答数字。

实际输出：38（正确答案是 40）

🔬 原理：Transformer 的"固定深度"与串行计算的矛盾

这是 LLM 最根本的结构性限制之一：一个 token 的前向计算经过的层数是固定的（比如 32 层）。 这意味着模型对每个 token 只能执行有限次数的"串行运算"。

h^{(l+1)} = h^{(l)} + \text{FFN}(\text{LN}(\text{Attn}(\text{LN}(h^{(l)})))) —— 深度 L 固定 ⇒ 单步推理的算子序列长度有上界。
  • 直接输出答案：模型必须在一两次前向传播内完成"48×2/3 → 32 ... 分给 4 个朋友 ... ×2"这一串运算， 这超出了它的串行计算预算，只能靠"模式匹配"猜一个看起来合理的数。
  • 思维链（CoT）为什么有效：让模型把中间步骤写成 token，每个新 token 都带来一次完整的前向传播。 生成 k 个中间 token，相当于把有效计算深度扩大了 k 倍—— 用 token 换计算量。
  • "只回答数字"加剧问题：你主动切断了它的草稿纸，等于禁用 CoT。
✅ 正确做法：放手让它推理，或用 few-shot CoT 
小明有 48 个苹果，他给了小红 1/3，然后小红把自己的苹果平均分给 4 个朋友，
每个朋友又给了小明 2 个。请问最后小明有多少个苹果？

请一步一步推理，写出每一步的计算过程，最后单独一行输出「答案：X」。

---
示例格式：
问题：10 个球，送出 1/2，再收到 3 个。
推理：
- 送出：10 × 1/2 = 5
- 剩余：10 − 5 = 5
- 收到 3 个：5 + 3 = 8
答案：8
---
❌ 直接答 输出 "38"。多步算术题准确率在中等规模模型上常低于 50%；步骤越多、数字越不整齐，崩塌越快。
✅ CoT 分步 "48 的 1/3 是 16，送出后剩 32。小红有 16 个……最后小明有 32 + 8 = 40。答案：40。" 准确率显著提升。
💡 进阶技巧：① Zero-shot CoT——只需加一句"Let's think step by step"（中文："我们一步一步来分析"）； ② Self-Consistency——用 temperature>0 采样 5–10 条推理链，对最终答案投票，准确率再涨一截； ③ Program-of-Thought——让模型生成 Python 代码而不是心算，交给解释器执行。

🎲 温度参数乱设，要么车轱辘话要么胡说八道

参数坑 采样策略 / softmax 温度
❌ 错误示例（两种典型翻车） 
[场景 A] 抽取合同里的甲乙方名称和金额
参数：temperature = 1.3, top_p = 1.0
→ 结果：模型"发挥"出了合同里根本没有的条款，把「壹佰万元」写成「一百多万元」。

[场景 B] 写 10 条不同角度的广告 slogan
参数：temperature = 0.0（贪心）
→ 结果：10 次调用返回的几乎是同一句话，只是标点略有不同。
🔬 原理：温度在重新塑形概率分布

温度 T 作用在 softmax 上，直接改变整个概率分布的"尖锐程度"：

p_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}
  • T \to 0：分布趋近 one-hot，等价于 argmax 贪心 → 确定、可复现，但单一、死板，容易导致重复。
  • T = 1：使用模型原始分布。
  • T > 1：分布被"抹平"，长尾 token 概率被抬高 → 多样但容易跑偏、出现幻觉。 T = 1.3 时，原本概率 0.1% 的 token 可能被放大 10 倍以上。

top_p（核采样）是另一层保险：只保留累积概率达到 p 的最小 token 集合。它和温度是配套的： 温度抬高长尾后，top_p 负责把最离谱的长尾切掉。

任务类型temperaturetop_p理由
提取 / 分类 / 结构化输出0.0 – 0.20.9 – 1.0要的是确定性，不是创造力
代码生成 / 数学推理0.0 – 0.30.95语法与逻辑不能发散
问答 / 摘要0.3 – 0.60.9兼顾忠实与自然
文案 / 头脑风暴 / 创意0.8 – 1.10.95需要多样性
需要极端多样性1.0 – 1.30.95–0.98配合去重与人工筛选
✅ 正确做法：按任务分层配置 + 多样性用采样多次而不是拉高温度 
[合同信息抽取]
temperature = 0.0, top_p = 1.0, response_format = json_schema
→ 确定性输出，字段稳定可解析。

[生成 10 条不同角度的 slogan]
temperature = 0.9, top_p = 0.95, n = 10      # 一次采样 10 条
或：temperature = 0.8, 调用 10 次并做语义去重
→ 多样性来自采样次数和 top_p，而不是把 T 拉到 1.5 让它开始胡说。
❌ 一个温度打天下 抽取任务用 T=1.3 → 幻觉与字段漂移；创意任务用 T=0 → 十次调用九次一样。
✅ 按任务分层 抽取用 0、推理用 0.2、创意用 0.9。上线后把温度和 top_p 写进配置并与 prompt 版本一起管理。
⚠️ 常被忽略的一点：temperature = 0 并不保证 100% 可复现——批处理、并行计算、硬件差异都会带来微小数值抖动。 如果业务真的需要强确定性（比如缓存 key），请自行做输出归一化与结果校验。

🕳️ "中间信息丢失"：塞得越多，答得越差

结构坑 lost in the middle / 上下文窗口 高频
❌ 错误示例 
[把公司全部 50 页员工手册原封不动贴进 prompt，共 38000 字]
[然后问：]

我的年假有几天？可以跨年累积吗？
🔬 原理：窗口容量 ≠ 有效利用能力

这就是坑 01 的同族病，单独列为一件展品是因为它在 RAG 场景里太常见了。核心结论来自 Lost in the Middle 等研究：

  • U 形注意力曲线：答案位于上下文开头或结尾时准确率最高；位于中间时准确率显著下降， 在长上下文中甚至可能低于"完全不提供文档"的闭卷表现。
  • 注意力被稀释：softmax 归一化意味着总权重是 1。20000 个 token 里塞进 1 个关键句，那一句分到的权重自然微乎其微。
  • Hmm，那"更长窗口"没用吗：有用，但它是"上限"而非"有效容量"。100 万 token 的窗口不代表模型能在里面做精准检索—— 这更像是一间巨大的仓库，不代表你能在里面三秒找到那根针。
  • 干扰信息主动伤害：与问题无关的段落不只是"占位"，它还会提供误导性的近邻语义，把模型带偏。
✅ 正确做法：检索优先 + 重排 + 分块摘要 + 位置策略 
# 步骤 1：检索（不要贴全文）
query = "年假 天数 跨年 累积"
→ 向量检索 + BM25 混合召回 Top-20 段落

# 步骤 2：重排（Rerank）
→ 用 cross-encoder 重排，取 Top-3 最相关段落

# 步骤 3：按"关键信息靠两端"排布
[任务指令]
[最相关的段落 → 放最前面]
[次相关的一段 → 放中间]
[第三相关的一段 → 放最后]
[再次复述问题]

# 步骤 4：要求引用
只依据上面提供的段落回答，每句话后标注来源段落编号。
若段落中没有相关信息，回答「手册中未提及」。
❌ 全文粘贴 38000 字 关键条款落在第 22 页中间，模型答"未提及"或编造"15 天"。 同时成本飙升、延迟翻倍。
✅ 检索 3 段 + 位置优化 相关条款原文进入 prompt，回答准确且带引用，token 消耗降到 1/20。
💡 三条实用策略： ① 减少绝对长度比优化排布更有效——优先做检索和重排； ② 必须放长文时，把最相关的内容复制一份放到末尾； ③ 用"分块 → 逐块抽取 → 汇总"的两阶段流程替代"一口气读全文"。

👤 代词指代不清，模型只能猜

原理坑 指代消解 / 歧义
❌ 错误示例 
把这个功能改一下，让它更好用一点，然后把那个也顺便调整下。
另外上次说的那个问题也一起处理了吧。
🔬 原理：多轮对话里，指代要靠"猜"来消解

模型没有真正的对话状态机，它做指代消解（coreference resolution）的依据是上下文里的统计关联。 当上下文里存在多个候选先行词时，模型只能给出一个概率分布下的"合理猜测"：

P(\text{指代对象} \mid \text{"它"},\ \text{上下文}) —— 候选越多、越相似，分布越平坦，模型越可能猜错。
  • "这个功能"：前文提到过 3 个功能，模型无从判断是哪一个。
  • "更好用"：是一个没有任何可操作定义的模糊目标——降低点击步数？提高加载速度？改文案？
  • "那个"：纯粹的空白指代，模型只能靠"最常出现的名词"来填，极不可靠。
  • "上次说的那个问题"：跨会话引用。如果历史里没有，模型会开始编造一个问题，然后煞有介事地"处理"它——这是幻觉的温床。
  • "一起处理"：三件事混在一个请求里，模型注意力分散，往往只做了最后一件。
✅ 正确做法：显式指代 + 可验证目标 + 单请求单任务 
## 任务 1：优化「批量导出 CSV」功能（/export 页面）
目标：把用户完成导出的操作步数从 5 步降到 3 步以内。
具体做法：把「筛选 → 确认 → 选格式 → 命名 → 下载」合并为
「选格式 → 下载」两步，筛选沿用列表页当前条件。
验收标准：路径长度 ≤ 3 次点击。

## 任务 2：调整「导出文件名」规则
现状：固定为 export.csv
期望：改为 {业务名}_{YYYYMMDD}.csv，例如 orders_20261103.csv

## 请先复述你对这两个任务的理解，确认无误后再给方案。
❌ 代词 + 模糊目标 模型改造了错误的页面，或直接反问"请问是哪个功能"。来回沟通 4 轮，比一开始说清楚还费时间。
✅ 显式 + 可验证 有路径、有目标数字、有验收标准。而且让模型"先复述理解"，成本极低，却能拦住 80% 的误解。
🩺 一条铁律：凡是能用名词说清楚的，绝不用代词。 "把它优化一下" → "把 /checkout 页面的表单校验从提交后改到失焦时触发"。 如果怕自己啰嗦，可以搜一下"Bob 测试"：把 prompt 给一个完全不熟悉项目的同事看，他能不能准确执行？
10

🤹 一次性让模型干八件事

结构坑 任务分解 / 注意力预算
❌ 错误示例 
帮我读完这篇论文，然后：1. 翻译摘要；2. 总结三个创新点；3. 列出所有实验数据集；
4. 批判它的方法缺陷；5. 提出三个改进方向；6. 生成一个剪藏用的 Markdown 卡片；
7. 找出里面所有错误的引用格式；8. 顺便推荐五篇相关论文。
全部一次输出完，格式要整齐。
🔬 原理：注意力是稀缺资源，约束越多漏得越多
  • 注意力预算有限：模型要在一次生成中同时满足 8 个不同的格式与内容要求，注意力被切分成 8 份， 每一项都只能分到薄薄一层。
  • 指令遵循是有成本的：研究表明，随着 prompt 中并列约束数量的增加，单条约束的遵循率会显著下降—— 这就是"约束疲劳"。经验上超过 5 条并列要求，漏项就开始成为常态。
  • 任务性质冲突：翻译要求逐字忠实，总结要求抽象压缩，批判要求发散质疑—— 把它们塞在同一次生成里，模型会在不同"模式"之间摇摆，输出品味混乱。
  • "格式要整齐"是空约束：没有指定具体格式，模型自己发挥的八段式往往长短不一、层次混乱。
  • 无法局部重试：一旦第 5 项崩了，你只能整段重来。
✅ 正确做法：拆成链式调用，每步只做一件事 + 给模板 
# Step 1 — 翻译摘要（纯转换任务，temperature 0.2）
输入：论文摘要原文
输出：中文译文，保留专业术语的英文原文加括号

# Step 2 — 总结创新点（输入 Step 1 的译文，temperature 0.3）
输出：恰好 3 条，每条格式「创新点：… ｜ 相比现有方法：…」

# Step 3 — 列数据集（纯抽取，temperature 0.0）
输出 JSON: [{"name":"","size":"","domain":""}]

# Step 4 — 批判与改进（合并为一个思辨任务，temperature 0.6）
输出：3 条「局限 → 改进方向」配对

# Step 5 — 生成卡片（模板填充，temperature 0.2）
按下面模板填充，缺失字段写 "N/A"：
## {{标题}}
- 任务：{{}}
- 方法：{{}}
...
❌ 八合一 实测常只完成 5–6 项，第 7、8 项基本消失；输出冗长且中途质量下滑；任何一项不满意都得全量重跑。
✅ 拆链串行 每一步输出都短质量高，可单独重试、可缓存、可用程序校验；总 token 成本往往反而更低。
💡 拆分判断标准：如果一个子任务的输出是另一个子任务的输入 → 串联； 如果两个子任务互不依赖 → 并行走两次调用（甚至用不同模型：抽取用便宜模型，批判用强模型）。 单次 prompt 的硬约束建议 ≤ 5 条。

📏 不指定长度：要么两句话，要么一本书

格式坑 输出长度控制
❌ 错误示例 
介绍一下什么是 Transformer。

可能输出 A（共 30 字）：
"Transformer 是一种基于自注意力机制的神经网络架构。"

可能输出 B（共 1400 字）：
从 2017 年论文讲起，讲编码器解码器、多头注意力、位置编码、残差、 讲 BERT 和 GPT 的区别，讲应用场景与局限……最后还附了参考文献。

🔬 原理：长度由"训练分布 + 解码过程"共同决定
  • 没有长度信号时，模型按训练数据里"这类请求通常配多长的回答"来采样。这个分布非常宽， 而且对提示词的细微措辞极其敏感。
  • EOS 是学出来的：模型在哪个 token 输出结束符，取决于它认为"答案完整了"。你没有定义"完整"，它就用平均长度来猜。
  • max_tokens 是硬截断：设太小会在句子中间被切断；设太大又给了模型啰嗦的空间。它不是长度控制手段， 而是安全阀。
  • 长度无约束会连带拖垮格式：想放入 UI 卡片位置的内容，如果没有字数上限，几乎必然溢出。
✅ 正确做法：显式字数区间 + 结构约束 + 参考样例 
介绍一下什么是 Transformer，面向有编程基础但不了解深度学习的读者。

要求：
- 总长度 180–220 字（中文汉字计）
- 结构固定为三段，每段一句话：
  ① 一句话定义（它是什么）
  ② 核心机制（自注意力在做什么，用一个类比）
  ③ 为什么重要（解决了什么旧问题）
- 不出现数学公式，不出现英文缩写（除非首次出现时给出全称）
- 全文不使用加粗和列表符号

参考样例（不同主题，仅示范长度与语气）：
"什么是向量数据库？它是专门存储和检索高维向量的数据库，把语义相似度变成可计算的距离。
核心机制是近似最近邻搜索——不追求找到最精确的那一条，而是在毫秒内找到足够好的一批。
它让『按意思搜索』第一次变得工程可行，此前这只能靠关键词碰运气。"
（共 152 字）
❌ 只说"介绍一下" 输出长度方差极大（30 字到 1500 字都可能），完全无法嵌入固定高度的 UI 组件。
✅ 字数区间 + 三段式 + 样例 输出稳定落在 190±15 字，结构一致，可安全渲染进卡片。
⚠️ 注意"字数"对模型是个软约束。模型无法精确计数 token 或汉字。 实践做法：① 给出区间而不是精确值；② 用"三段/三点/每点一句话"这种结构约束间接控长； ③ 关键场景在程序侧做长度校验，超限就重新生成或让模型"压缩到 X 字以内"。

🌈 "尽可能好一点"——无法验收的模糊目标

参数坑 目标函数 / 可验证性
❌ 错误示例 
请用最专业的方式，尽可能好地、高质量地完成这个任务，
要体现出你的能力和水平，做到最好，让人眼前一亮。
（任务：把这段话写得更通顺一些）
🔬 原理：模型在优化你给出的"可观测目标"

"好""专业""高质量"对模型来说不是一个方向，而是一个噪声很大的向量。 这类词在训练数据里总是和"冗长、华丽、加粗、加 emoji、堆专业术语"共现—— 所以模型会把这些表面特征当成"satisfying the request"：

\text{argmax}_y\; P(y \mid \text{"尽可能好"}) \;\approx\; \text{"人类写的、看起来很用心的长文本"}
  • "最专业的方式"常常变成"术语最多的方式"——把"修一下这句话"变成满篇"赋能""抓手""闭环"。
  • "让人眼前一亮"往往变成加 emoji、加感叹号、加修辞排比。
  • 无法验收：你没法说"这个不够好"，因为你没定义过"好"。
  • 和原始任务冲突：任务是"写得更通顺"，结果被改写成了一篇更长的文章，原有信息反而被稀释。
✅ 正确做法：把"好"翻译成可检查的判定条件 
把下面这段话改得更通顺、更易读。

## 具体标准（全部满足）
1. 句子平均长度 ≤ 30 字，最长单句 ≤ 45 字
2. 不用被动语态，主语明确
3. 删除所有冗余修饰词（"非常""十分""进行了"等），信息量不变
4. 保持原意不变，不新增任何事实
5. 总长度不超过原文 +10%

## 输出格式
第一行：改写后的文本
第二行起：逐条说明你做了哪些修改（格式「原句 → 改句 → 原因」）

原文：
我们这边呢，其实是针对公司的这个运营流程进行了一个比较全面的、系统性的梳理和优化工作……
❌ "尽可能好 + 让人眼前一亮" 输出变成一篇 500 字的"赋能闭环方法论"，加粗和 emoji 齐飞，离"改通顺"十万八千里。
✅ 5 条可检查标准 输出朴素、通顺、原意不失。而且你能拿着这 5 条逐项验收——甚至写个脚本自动测平均句长。
💡 万能替换公式：把每个形容词都翻译成可观测的量。
"专业" → "使用行业标准术语，每个术语首次出现给全称"
"简洁" → "≤120 字，无冗余修饰词"
"严谨" → "每个结论后标注来源，不确定的写『待验证』"
检验方法：如果一段 prompt 无法用来做打分验收，那它就不是一条有效指令。
